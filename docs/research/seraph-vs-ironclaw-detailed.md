# Detailed Seraph and IronClaw comparison

Comparative, privacy and security wording remains bounded by the
[strategy claim ledger](./19-strategy-claim-ledger.md).

**Inspected:** 5 October 2026, Europe/Warsaw. **Owning request:** [#954](https://github.com/seraph-quest/seraph/issues/954). This research informs the [guardian capability roadmap](/guardian-capability-roadmap); it does not accept a competing architecture or establish broad superiority.

The [shared Seraph baseline](./seraph-capability-baseline-2026-10-05.md) distinguishes the inspected `develop` and `main` revisions, #899/#953 integration, platform receipts and external-provider evidence. This comparison uses that bounded operator baseline. Historical status entries and benchmark registries are not silently promoted to live modern-provider proof.

Evidence classes in this document are **implementation source**, **official documented behavior**, **declared limitation**, **historical/local receipt** and **not verified here**. They are independent of capability lifecycle states in Seraph's [Documentation Contract](/docs-contract). “Blocked” describes work/prerequisites; it is not a capability lifecycle label. No IronClaw instance, fresh model call, benchmark, external integration account or TEE client verification was run.

## Contradictions and research limits

IronClaw's release sandbox README describes a wired production backend, while its [parity row L753](https://github.com/nearai/ironclaw/blob/b011eb3932a0e1ab8bbe833893599ca9ae4925c5/FEATURE_PARITY.md#L753) still says no production execution backend is wired. Treat the implementation and owning crate contract as positive source evidence, preserve the contradiction, and require live acceptance before asserting deployment reliability. Its README PostgreSQL comparison is incomplete relative to current embedded-local storage docs. README privacy prose does not establish encryption of every local file or prevent all local debug logging.

Seraph's status contains historical local-Gemma/GPU and stronger-proof inventories alongside the current OpenRouter phase. Those historical entries do not override ADR-006 or prove a current external model route. Optional Linux sandbox and companion receipts do not establish macOS native execution. Local fixtures, implementation source, hosted CI, real account readback, paid model behavior and human usefulness are separate evidence classes.

No benchmark in this comparison supports broad “better,” “safer,” “more autonomous,” or “private by default” claims. Unknowns should produce bounded follow-up evidence, not invented absence or automatic scope expansion.

## Roadmap implications

The sequence extends existing Seraph capability owners: [M1 purpose-specific inference](/guardian-capability-roadmap#m1-purpose-specific-inference), [M2 fresh goals and cited opportunities](/guardian-capability-roadmap#m2-evidence-cited-opportunities), [M3 reviewed bounded plans](/guardian-capability-roadmap#m3-reviewed-opportunity-plans), [M4 reviewed usefulness learning](/guardian-capability-roadmap#m4-reviewed-intervention-usefulness), then [conditional M5 verified NEAR inference](/guardian-capability-roadmap#m5-verified-near-inference). M5 remains blocked until reviewed architecture/trust prerequisites are fixed. The purpose of M1–M4 is an observable useful guardian journey, not another proof-only registry or competing lifecycle runtime.
