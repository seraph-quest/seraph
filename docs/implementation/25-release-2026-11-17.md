# Seraph v2026.11.17 Release Notes

The November 17 release line lands the remaining slices of the backend test
determinism programme and closes most of its follow-ups, lets the paired macOS
daemon post window context and notification receipts with its paired-edge
credential, enforces the screenshot size cap and retention on stored captures,
adds an opt-in GitHub activity source that uses the operator's local `gh`
login, and fixes a lifecycle transition race that let a status poll report a
finished transition while the domain was still blocked.

## Highlights

### Daemon and observer

- The daemon's
  [window context post](https://github.com/seraph-quest/seraph/pull/1250)
  (`POST /api/observer/context`) was always refused with
  `403 mutation_origin_required`, because the daemon sends no Origin. A request
  with neither an Origin nor a cookie now takes the same paired-edge credential
  check as screenshot uploads (Bearer and `X-Seraph-Node-*` identity, an active
  pairing and its policy). Authentication runs before any body byte is read and
  the body is bounded to 1 MiB. Requests with an Origin keep the browser origin
  and operator-session rules unchanged. An unpaired daemon still posts without
  a credential, is refused, and logs once that context posting needs pairing.
- The daemon's
  [notification receipts](https://github.com/seraph-quest/seraph/pull/1261)
  (`display-attempted`, `ack` and `fail`) take the same native path. The
  paired-edge credential must belong to the same operator that made the claim
  (`pairing_owner_mismatch` otherwise), the body is bounded to 4 KiB, and
  `X-Seraph-Daemon-Id` must still match the worker. Dismiss, test, reconcile and
  other notification routes keep the browser Origin rule. A live check on a
  paired daemon was not run for this change.
- [Stored screenshots are capped](https://github.com/seraph-quest/seraph/pull/1265):
  `archive_max_mb` and `archive_retention_days` are now enforced. The backend
  prunes its private upload store after each accepted upload and in the
  `screen_cleanup` job; the daemon prunes its own archive, and only under
  limits it received from the backend in the same process. A capture is stored
  in one place, not both. A pruned image reads as unavailable
  (`image_available: false`) rather than as an error. Settings → Artifact
  storage shows a read-only "Stored captures" row. On upgrade, the daemon's
  first successful settings fetch applies the configured retention (default
  365 days) and cap to the existing archive. **Partial:** the cap applies per
  store, so after a topology switch or a run of failed uploads the two stores
  together can hold up to twice the cap until retention ages the idle store
  out. Saving screenshot settings while the settings file is unreadable can
  write the default limits back to disk; that and smaller review items are
  tracked in [#1266](https://github.com/seraph-quest/seraph/issues/1266).

### GitHub activity source

- [Slice 1 of #1264](https://github.com/seraph-quest/seraph/pull/1267) adds an
  operator opt-in source (Settings → GitHub → **GitHub activity for reports**)
  that reads the operator's own GitHub activity for a day through their local
  `gh` login and stores it as provenance rows. `gh` is found only at fixed paths
  or one absolute path the operator enters, never through `PATH`, and is run
  with one fixed read-only `gh api --method GET` argv over a closed endpoint
  table, in an environment built from nothing (no token, host, config or proxy
  variables). A run makes at most 120 calls across at most 10 repositories,
  with no retry. Two effective-grant rows describe it: `github_activity`
  (observation) and `github_activity_model` (model analysis, denied unless the
  operator ticks it); revoking either switches the source off. No token is
  stored. **Partial:** the end-of-day report does not read these rows yet
  (slice 2 of [#1264](https://github.com/seraph-quest/seraph/issues/1264));
  reviews and comments are not collected; no test ran against a real `gh`
  login, so behaviour with one is unverified until the operator's own **Check
  gh login**. The `gh` token has full scope: Seraph only issues read GETs, but
  the argv builder is the only limit. Restore and identity follow-ups, including
  a source that stays active after its owning login identity is lost, are
  tracked in [#1270](https://github.com/seraph-quest/seraph/issues/1270).

### Runtime lifecycle

- A [lifecycle transition keeps its claim](https://github.com/seraph-quest/seraph/pull/1268)
  until its reactivation settles. `RuntimeLifecycle.transition` used to release
  the domain claim before reactivating at the new epoch, so a status poll could
  see the transition succeeded while the domain was still `blocked` at the old
  epoch. The claim now stays as `reactivating` until the new activation, or the
  reason it is blocked, is in place; a second transition is refused until then.
  This was the cause of the intermittent `backend-tests (8)` failure on
  `develop`. **Partial:** hardening of the reactivation bypass, the status left
  after a failed reactivation, a regression variant that needs no Cordis build
  and docs on when a transition is finished are tracked in
  [#1269](https://github.com/seraph-quest/seraph/issues/1269).

### Process cleanup

- `run_command`'s
  [bounded pipe capture](https://github.com/seraph-quest/seraph/pull/1251) no
  longer waits for a descendant that still holds stdout or stderr after a
  timeout. The drain waits on a selector and a private wake pipe instead of
  blocking in a buffered read, so `finish()` keeps its bound. Partial output on a
  held pipe is now captured; before, it was lost.
- If [pipe capture setup fails](https://github.com/seraph-quest/seraph/pull/1260)
  after the child has started (for example `EMFILE`), `run_command` now stops
  and reaps the child and closes its pipes before re-raising the original error.
- The repository worker
  [kills and reaps a child on any error path](https://github.com/seraph-quest/seraph/pull/1249)
  and closes its pipes once the process group is empty, which removes the last
  per-file leak exception. A Calendar or Mail model call that outlives its bounded
  wait is now tracked, so shutdown waits for its late writes; its output is
  never used.
- [`session_scope` rolls back on cancellation](https://github.com/seraph-quest/seraph/pull/1262):
  a cancelled unit of work drops its pending work-board events and rolls back
  explicitly, and the original `CancelledError` still reaches the caller.

### Test determinism

[#1217](https://github.com/seraph-quest/seraph/issues/1217) makes the backend
suite independent of load, timing and garbage collection. With this release
all eight slices are merged (1, 2, 3 and 7 shipped in v2026.11.15). The
programme stays open for the remaining database seam gaps in
[#1241](https://github.com/seraph-quest/seraph/issues/1241).

- Slice 4, [sync primitives](https://github.com/seraph-quest/seraph/pull/1240):
  `tests/support/sync.py` adds signals, gates, `assert_blocked`, `settle` and a
  `wait_until` that raises with the last observed state instead of falling
  through. Elapsed-time asserts became causal assertions, and sleep-then-assert
  negative proofs now observe the task at its blocking point first. Ratchet
  counts fell from 174 to 65 sleeps and from 65 to 9 clock comparisons. Tests
  only.
- Slice 5, a [single database seam](https://github.com/seraph-quest/seraph/pull/1239):
  each test gets its own SQLite file built with the production engine factory,
  pragmas and pool, installed as the default database, so every `get_session`
  caller reaches it through the real state gate. The shared in-memory StaticPool
  connection is gone, and a sentinel fails any test that connects to the
  canonical engine. Production engine configuration is pinned and unchanged.
  [A follow-up](https://github.com/seraph-quest/seraph/pull/1254) moves the
  remaining `get_session` patches onto injection seams (ratchet 119 to 4) and
  reports a canonical-engine connection made after a test's teardown.
  **Partial:** `accounting_db` and the forked publication child still run
  without production pragmas or foreign keys, and per-file engines remain
  (#1241 items 1, 2 and 4).
- Slice 6, a [process-state registry](https://github.com/seraph-quest/seraph/pull/1243):
  every module-level mutable in `backend/src` is registered and restored or
  reset after each test, and a test fails if it leaks a pending task, a running
  thread or a child process. The remote-inference admission broker is reached
  through an accessor. Bounded HTTP stream reads now close their iterators, a
  publication `git` leader is reaped on Darwin, and every background spawn in
  `src` is tracked.
- Slice 8, a [clock seam](https://github.com/seraph-quest/seraph/pull/1242):
  production time is read through `get_clock()`; `SystemClock` makes exactly the
  calls it replaces, and tests advance a `FakeClock` explicitly. Eighteen modules
  read time only through the seam, enforced by the ratchet with zero tolerance.
  Realtime markers fell from 16 to 5. No production deadline, gate or TTL
  changed.
- Follow-ups: the ratchet resolves `__import__` and `importlib.import_module`
  ([#1262](https://github.com/seraph-quest/seraph/pull/1262)), and the dispatcher's
  active worker table is registered. The intermittent research recovery test
  ([#1252](https://github.com/seraph-quest/seraph/pull/1252)) lapses its lease at
  the declared restart point instead of sleeping (50 of 50 hosted runs under
  contention). The [#1227 review follow-ups](https://github.com/seraph-quest/seraph/pull/1253)
  add `cancellation_pending` coverage on the fake clock and record that the
  research cancel wait was not lock contention; production is unchanged.

## Boundaries and validation

The GitHub activity source runs only after the operator enables it, uses the
operator's own `gh` login with its full token scope, and feeds no report yet.
The daemon authentication changes add a native path only for requests without
an Origin or cookie; the browser Origin rule is not loosened. No live provider
availability, billing or answer quality is claimed.

Known open test and cleanup follow-ups:
[#1241](https://github.com/seraph-quest/seraph/issues/1241) (remaining
database seam gaps),
[#1215](https://github.com/seraph-quest/seraph/issues/1215) (scheduler
lifecycle test, Cordis host stops admitting on a loaded runner),
[#1266](https://github.com/seraph-quest/seraph/issues/1266) (screenshot settings
saved while the file is unreadable),
[#1269](https://github.com/seraph-quest/seraph/issues/1269) (lifecycle
transition claim hardening) and
[#1270](https://github.com/seraph-quest/seraph/issues/1270) (GitHub activity
restore and identity wiring before slice 2).

The [release issue](https://github.com/seraph-quest/seraph/issues/1271) carries
the release-head checks and publication readbacks; each linked PR carries its own
focused validation and review. No app production deployment is implied.
